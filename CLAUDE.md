# Architecture diagrams

Maintain the system architecture diagram in PlantUML. Whenever the architecture
changes or the diagram is edited, update its `.puml` source locally, compile it
with PlantUML, and open the generated diagram for visual review before reporting
completion. Do not treat a diagram update as complete until compilation succeeds
and the rendered output has been opened.

# Deploy workflow

This repo holds docker-compose stacks that get deployed to a remote VM. The
VM is reachable over SSH as the host alias `vm` (see `~/.ssh/config`;
currently `ubuntu@161.104.107.172`).

**Always author and edit compose files, `.env.example`, and scripts locally
in this repo first.** Never hand-build config by poking around on the VM
(no ad-hoc `find`/`sudo`/interactive edits over SSH to construct a stack).
The VM is a deploy target, not a place to improvise from.

**Nothing auto-deploys.** A `git push` does not touch the VM — there is no
CI/CD wired up. Deploys are manual, via `scripts/deploy.sh`.

To ship a stack:

1. Write/update the `docker-compose.yml` (and any `.env.example`,
   `scripts/`) locally, matching the pattern already used for the Zabbix
   stack (own named volumes, own bridge network, `restart: unless-stopped`,
   secrets sourced from a gitignored `.env` generated by a `gen-env.sh`
   script rather than committed).
2. Run `scripts/deploy.sh <local-dir> <remote-dir> [health-url]`, e.g.:
   - `scripts/deploy.sh prometheus prometheus http://localhost:9090/-/healthy`
   - `scripts/deploy.sh . zabbix http://localhost:8080`

   This rsyncs the stack to `~/<remote-dir>` on the VM (never touching a
   pre-existing remote `.env`), runs `docker compose up -d`, then checks
   container status and the health URL. It prints one `OK`/`FAIL` line —
   `docker compose logs` only gets dumped automatically on failure, so you
   don't have to go fetch logs by hand after every deploy to know it worked.

Each stack should get its own compose project `name:` and its own Docker
network so multiple stacks (Zabbix, Prometheus, etc.) coexist on the VM
without port/volume/network collisions. Check `ssh vm "docker ps -a"` and
`docker network ls` before adding a new stack to avoid clashing container
names or host ports.
