# Бриф кейса (исходные данные заказчика)

## Цель

Спроектировать и продемонстрировать веб-платформу управления оповещениями,
снимающую информационный шум и потери от простоя в пилотном периметре БРД —
без обработки реальных персональных данных и без зависимости от недоступного
в рамках кейса домена AD, с гибкой (не жёстко зашитой) ролевой моделью и
классификацией событий.

## Задачи

- разработка дашборда администратора;
- разработка личного кабинета сотрудника и администратора;
- интеграция с TrueConf, системами мониторинга.

## Образ результата

Веб-портал с личным кабинетом (список текущих аварий, self-service подписки,
история) и админ-панелью (настраиваемые группы пользователей, настраиваемая
классификация критичности, правила маршрутизации, near-online дашборд),
интегрированный с TrueConf для доставки уведомлений и авторизации без реального
AD, принимающий поток синтетических разноформатных событий и обрабатывающий их
минимум одним рабочим ИИ-сценарием, с приложенным экономическим обоснованием.

## БТ7. Интеллектуальная обработка алертов

Система должна поддерживать интеллектуальные функции для снижения шума,
ускорения обработки алертов и повышения точности маршрутизации: дедупликацию,
фильтрацию шума, приоритизацию, маршрутизацию, классификацию и декомпозицию
инцидентов.

| ID | Требование |
| --- | --- |
| ПТ7.1 | Интеллектуальные функции должны работать в режимах: off, shadow, suggest, assisted auto, full auto. |
| ПТ7.2 | Для каждой функции должен быть задан уровень автоматизации, порог уверенности и fallback-поведение при недоступности ИИ. |
| ПТ7.3 | ИИ не должен блокировать приём, регистрацию и доставку критичных алертов при своей недоступности или низкой уверенности. |
| ФТ7.1 | Дедупликация: выявлять дубли по техническим и смысловым признакам, объединять с родительским событием, сохранять историю. Автообъединение — только при высокой уверенности. Критичные алерты не скрываются и не удаляются. |
| ФТ7.2 | Фильтрация шума: помечать возможные шумовые алерты и помещать в карантинную очередь. Автоподавление critical/high запрещено. |
| ФТ7.3 | Приоритизация: предлагать приоритет на основе критичности сервиса, severity, SLA, истории и связанных событий. Автопонижение приоритета critical/high запрещено. |
| ФТ7.4 | Маршрутизация: рекомендовать или назначать получателя на основе сервисного каталога, владельцев, команд, on-call и истории назначений. При низкой уверенности — triage-очередь. |
| ФТ7.5 | Декомпозиция: предлагать разбиение составных инцидентов на дочерние события с сохранением parent-child связей. На пилоте автоматическая декомпозиция отключена либо только при высокой уверенности и без дублирования уведомлений. |
| ФТ7.6 | Объяснимость: каждое решение ИИ содержит объяснение, confidence, использованные признаки, альтернативные варианты и версию модели. |
| ФТ7.7 | Обратная связь: пользователь может подтвердить, отклонить или переопределить решение ИИ с указанием причины. |
| НФТ7.1 | Аудит: все решения ИИ (предложенные, применённые, переопределённые) журналируются с моделью, версией, confidence, входными признаками и результатом. |
| НФТ7.2 | Fallback: при недоступности ИИ обработка продолжается по детерминированным правилам. |
| НФТ7.3 | Производительность: задержка ИИ не приводит к задержке доставки critical-алертов. |
| НФТ7.4 | Безопасность: в ИИ/LLM не передаются секреты, ПДн и иная чувствительная информация без разрешения. Текст алертов обрабатывается как недоверенные данные. |
